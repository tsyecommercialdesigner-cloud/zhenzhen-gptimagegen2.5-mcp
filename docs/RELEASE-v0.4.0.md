# v0.4.0 发布与迁移说明

本版基于 PR #9、PR #10 的同步批量、异步自动轮询及迁移恢复能力。Windows 标准 CI、受控协议测试和安装检查与真实供应商、Host 验收分别记录。发布提交的完整 SHA、main CI、发布运行及全新安装结果随 Release 的 `release-evidence.json` 提供；发行包校验值见 `SHA256SUMS`。发布流程生成草稿，核对附件和证据后才正式公开；不覆盖旧 v0.3.1。

## 主要变化

- 新增 `run_image_batch`，同步每批最多 20 项，默认和最大并发 5；提供 12 Tools / 1 Prompt / 1 Resource。
- 异步每批最多 20 项，默认提交并发 5、最大 20；同一进程跨批次共享提交槽，不保证账号级或供应商内部执行并发。
- 单项生成/编辑入口可传稳定 `idempotency_key`；批量沿用 `(checkpointer, thread_id, task_id)`。收费 POST 不自动重发，未知结果不能换键重提。
- 服务运行时对已登记的异步任务按至少 90 秒间隔自动查询并保存，支持重启恢复和跨进程轮询租约；查询或保存暂时失败后继续原任务。终态失败或全部保存成功后停止轮询。
- 保存及重放校验文件哈希。批量持久清单保留脱敏下载错误，不持久化下载 URL、提示词或密钥。

## 升级与回滚

1. 停止所有使用同一安装目录的 MCP 子进程；记录原 SHA，备份 `.env` 及 ACL、整个 `.runtime`（包括存在的 WAL/SHM）、输出 `.tasks` 元数据和图片。不要在 SQLite 活动时直接复制数据库。
2. 按 [MANUAL](../MANUAL.md#5-启动排障) 获取固定 v0.4.0 标签，读取该标签 Release 附件中的完整提交并核对，锁定安装依赖。日常启动保持 `--no-sync`。
3. 首次使用检查点写入或后台轮询时，schema 1 自动迁移为 schema 2；保留旧身份、请求指纹和已知供应商编号。未知提交仍冻结，不能重发。旧单项 JSON 元数据不会自动导入轮询。
4. 完成免费协议发现后再启用实际 Host。新版本 Host 升级仍需单独验收；本轮没有升级维护者的 D 盘 v0.3.1 安装。

schema 2 不能直接交给旧程序使用。回滚须先停止新进程并保留新库及供应商编号；恢复升级前备份会缺失升级后新增任务，不能据此换键重提。优先保留原供应商编号以便人工核对，不通过删除数据库、硬重置或清空安装目录回滚。

## 验证与已知限制

- 发布准备基线已通过 115 项受控测试，包含迁移中途 SQL 错误回滚、子进程硬退出、备份恢复、原身份查询恢复以及不重复收费提交。发布候选提交须再次通过 Windows PR CI、合入 CI，以及发布流程的构建、审计和独立锁定安装检查；结果以对应运行和发布证据为准。
- 历史一次 Flare 五路同步测试的 5 个请求均返回 HTTP 200 和图像结果，但本地保存全部失败。当时未保留具体下载错误，根因仍未确认。新增诊断修复不能补回历史错误，也不表示真实端到端交付已通过；本轮不追加收费测试。
- 请求尺寸可能与供应商返回像素不同。官转高级参数、Images SSE、真实 20 项生成、供应商长期并发配额及计费币种仍需按需核实。
- 本机 v0.3.1 的 Codex 验收属于历史安装证据，不能当作 v0.4.0 已完成真实 Host 验收。其他 Host 和 Shell 覆盖边界见 [验证记录](VALIDATION.md)。

详细需求与回归记录见 [异步批量方案](ASYNC-BATCH-PLAN.md) 和 [验证记录](VALIDATION.md)。
